# WeXposedHook Java 代码结构

Xposed 模块源码：完整承载 X 3.0 壳（壳的 Java 层在 `app/libs/shell-runtime.jar`，
`com.android.x.XposedInit` 是壳入口），并接管其授权校验入口。

模块本身是一个完整 APK，包含自己的 Activity：

- `github.shadowbaby.wechatxposed.hook.ui.MainActivity`：模块主界面（桌面图标 / LSPosed「模块设置」进入）。
- `com.android.x.MainActivity`：同一实现的桥接类，保留壳包名入口。
- 微信进程内的功能入口由 `hook/shell/` 负责：
  - `SettingsEntry`：微信「我 → 设置」最上方插入「更多」。
  - `PlusMenuEntry`：微信首页「+」菜单最下方插入「X」。
  - `FeatureSettings`：两个入口点击后都调用功能 dex 里的设置页控制器 `c.ˏᴵ.ʻᵔ`，
    页面（标题/版本行/搜索/分类/开关/三点菜单）全部由功能包自己渲染，项目不重画 UI。

## 命名约定

- 入口类 `XposedInit` 直接放在 `hook` 下,其余按职责分包:`loader/dex`(dex 加载拦截)、
  `loader/util`(日志/解密/native)、`license`(授权库)、`deploy`(内置载荷与启动自检)、
  `support/pack`(功能包数据面)、`support/guard`(反禁用与壳校验)、`support/feature`(项目附加特性)。
- 字段直接用语义名(`WX_COMPONENTS` / `mode` / `componentId` / `bypassMode` / `hostClassLoader` 等);
  字符串常量集中在各类顶部,不散落在方法体里。
- **敏感常量不写明文**:微X 混淆类名、校验方法名、功能列表、AES 密钥、锚点串、功能包清单
  一律写成 `Secret.of(SecretConstants.XXX)`。明文集中在 `scripts/secrets_table.py`,
  构建前编码成密文写进 `SecretConstants.java`,运行时由 `libwexhook.so` 解码
  (见「敏感常量编码」一节)。
- 微X自身混淆过的类名(如 `c. َˉ.ᴖˉ`)按 `\uXXXX` 转义写在常量里,避免编码依赖;
  这些名字只作为字符串传给 `findClass`,与 Java 包名无关。
- 这些名字必须用**点号**分隔(`ʾⁱ.ⁱʽ`)。dex 描述符里的斜杠形式(`Lʾⁱ/ⁱʽ;`)直接交给
  `Class.forName` 会抛 `ClassNotFoundException`,类名对了也解析不出来;`tests/dex-probe/` 专门钉这条。

## 运行时流程

1. `XposedInit.initZygote` 挂 `dalvik.system.InMemoryDexClassLoader` 全部构造函数，并记下模块 APK 路径（`ModuleApk.remember`）。
2. 每次有 dex 通过内存构造器加载，`InMemoryDexLoadHook` 在当前 ClassLoader 里识别 X 3.0 组件并安装 hook；外层 PBE password 命中后，空 buffer 由 `FeatureDexInjector` 注入真实 dex。
3. `X3CallMethodHook` 按 `msgId`（130/132/150）与查询类型伪造校验结果与功能列表；`X3GuardBypass`/`X3SettingsBypass` 处理 params 与设置读取。
4. `FeatureCloseGuard` 阻止组件 finish/unload 清空功能表。
5. 微信主进程启动时,`XposedInit.handleLoadPackage` 调 `StartupCheck.run`:
   `FeaturePackRestorer` 检查 `files/x7_3.0`（基础 26 + 扩展 6），缺哪个就从 APK 内置载荷补写；
   `LicenseInstaller` 再按微信 prefs 里的登录账号补一次授权库。
6. 壳校验授权时把权威账号交给 hook（`CurrentAccount.remember`），启动自检据此再补一次库。
7. 微信主进程启动时,`HostVersionSpoof.install` 把客户端版本文件放在
   `files/X/wxh_client_version`：
   文件不存在时写入 `8.0.79`;LauncherUI.onResume 时把 `c64.xe.g` 提到该版本;
   进入钱包/转账白名单页面时临时还原真实版本,退出后恢复;启动约 30 秒后
   主动抓取一次升级页(24 小时 TTL)。小程序进程不再做 dex 扫描。

第 7 步是**辅助功能**:它跑在启动自检之后,`install` 内部吞掉所有异常,`XposedInit`
外面再兜一层,所以它失败不影响第 1–6 步的主功能。

## 敏感常量编码

release 开着 R8,标识符已经被混淆,但**字符串字面量不会**——`strings classes.dex`
就能直接读到微X 的混淆类名、58 项功能列表、AES 密钥。所以这些常量不以明文出现:

- `scripts/encode_secrets.py`:编码逻辑 + `NAMES` + 默认主密钥。**只在内部仓**(含密钥,不能公开);
- `scripts/secrets_table.py`:常量名 -> 明文,**只在内部仓提交**(公开仓同步时排除);
- `loader/SecretConstants.java`:构建前生成,只有密文;
- `app/src/main/jni/secret_crypto.inc`:主密钥(可被 `WXH_MASTER_KEY` 覆盖)+ HKDF/XOR 算法,**入库**;
- `app/src/main/jni/secret.c`:JNI 绑定与 UTF-8 → UTF-16(include `.inc`);
- 运行时 `Secret.of(SecretConstants.XXX)` 走 so 还原。

明文来源按优先级取(见 `encode_secrets.py` 的 `secrets_table`):

| 场景 | 来源 | 说明 |
|---|---|---|
| 内部仓 | `scripts/secrets_table.py` | 直接跑脚本(该文件只在内部仓) |
| 内部仓 CI(不想落明文时) | 环境变量 `WXH_SECRETS_B64` | 整张表 JSON 后 Base64,由 CI Secrets 注入 |
| 公开仓 | 无脚本,不生成 | 直接用同步过去的 `SecretConstants.java`(密文) |

公开仓没有 native 源码,构建本身不消费 `WXH_MASTER_KEY`;同步脚本 `publish_public.py`
用当前密钥重新编码明文表,逐项比对 `SecretConstants.java` 的密文,不一致直接中止同步。

脚本会拿 `NAMES` 校验明文表:缺项 / 多项都直接报错退出(缺项会让源码引用编译不过)。

编码是「HKDF-SHA256 按常量名派生子密钥 + 逐字节 XOR + 位置混合」再 Base64,
目的是让静态扫描拿不到明文、单项泄露不扩散,不是抗专业逆向。

密文格式 `"<常量名>:<Base64>"`:常量名随密文进 dex,运行时 so 拿它当 HKDF 的 salt
派生该常量专属的子密钥(`derive_subkey`),`Secret.of` 的签名因此不用改。

### 密钥下沉到 so

阶段 1 的纯 Java 版本把种子放在 dex 里,拿到密文就能解。现在:

- 主密钥只在 `app/src/main/jni/secret_crypto.inc` 里,编译进 `libwexhook.so`;
- 每项子密钥由主密钥 + 常量名经 HKDF-SHA256 派生(`derive_subkey`),
  Python 与 C 两份实现必须一致(`tests/secret-encoding/run.py --clang` 逐项比对);
- dex 里既没有明文也没有密钥,只有密文;`Secret.of` 全部走 JNI。

`SecretConstants.java` 由构建前的 `encodeSecrets` 任务(跑 `scripts/encode_secrets.py`)生成;
公开仓没有该脚本,任务自动跳过,直接用同步过去的密文表。
**密钥固定**:`MASTER_KEY`(32 字节)默认硬编码在 `secret_crypto.inc` 与 `encode_secrets.py` 两处,
必须逐字节一致;子密钥由它 + 常量名派生,与随机数无关,所以同一份明文表每次生成的密文相同。
**对称**:算法是「HKDF-SHA256 派生子密钥 + 逐字节 XOR + 位置混合」再 Base64,加解密同一把密钥,
没有公私钥对——不是 AES 那类密码学加密,只是让 `strings classes.dex` 拿不到明文。
**每项独立**:子密钥的 HKDF salt 是常量名,逆出某项推不出其它项。

**换主密钥**(要求 32 字节,`hex` 或标准 `Base64` 都行):构建时设一个环境变量
`WXH_MASTER_KEY`,Gradle 会同时喂给 clang(编 so)与 `encode_secrets.py`(生成密文),
重跑 `./gradlew assembleLegacyRelease assembleModernRelease` 即可,两边不会错配;
改完必须重编 so 并重装。详细步骤见 `README.md` 的「换主密钥」。

**不提供 Java 回退**:回退会把主密钥写回 dex,等于白做。两个 ABI 都产出
(`arm64-v8a` 与 `armeabi-v7a`,分别对应 64 位 / 32 位微信)。so 加载失败时
`Secret.of` 返回空串,让类查找干净地失败,而不是让模块崩在静态初始化里。

构建:`buildNativeSecret` 任务用 NDK 的 clang 直接编译(不走 ndk-build——
它拒绝含空格的工程路径),源码在 `app/src/main/jni`(只提交到内部仓),产物写进
`app/src/main/jniLibs/<abi>/libwexhook.so`。内部仓 gitignore 该产物、每次构建现编;
公开仓没有源码、直接把同步过去的 so 提交入库。两仓分工见 `README.md` 的「两个仓」。

改动敏感常量:改 `secrets_table.py` 后重新生成,不要手工编辑生成的两个文件:

```powershell
python -X utf8 scripts/encode_secrets.py
```

对应关系由 `tests/secret-encoding/` 逐项校验。

## 构建

需要 JDK 17 与 Android SDK 37(AGP 9.4.1 要求 Gradle 9.6+):

```powershell
JAVA_HOME=<JDK17> ./gradlew assembleRelease
```

> 功能包载荷由 `scripts/build_release_packs.py` 在构建时从 `xmetadata/wx7` 生成：
> 基础包写入 `.../wx30/x7_3.0.zip`（26 个文件），扩展包写入
> `.../wx30-ext/x7_3.0_ext.zip`（6 个文件）。基础包进入所有 APK，扩展包只进入 full，
> 生成物不随仓库提交。单 APK 壳用 `:app:assembleX30Replica`（`x30` build type，
> 无 R8）构建。

release 构建开着 R8(`minifyEnabled true`)。这对本模块是安全的,但**改动类结构/回调时
必须复核 `app/proguard-rules.pro` 的保留规则**,否则入口会被改掉:

- `assets/xposed_init` 里的类名由框架按字符串加载,`XposedInit` 必须保留原名。
- `XC_MethodHook` / `XC_MethodReplacement` 的 `beforeHookedMethod` / `afterHookedMethod` /
  `replaceHookedMethod` 由框架反射调用,规则里按方法签名 `-keepclassmembers` 保留
  (公开入口例外,会由 `-keep class XposedInit` 覆盖)。
- 微X 的类名(含 `c. َˉ.ᴖˉ` 这类)以字符串传给 `findClass`,与 R8 无关,不受影响。

加固相关的规则(见 `app/proguard-rules.pro` 注释):

- `-repackageclasses` / `-allowaccessmodification` / `-overloadaggressively`:
  把类压进同一个包、放宽访问修饰符、复用方法名,反编译后看不出原来的分包结构;
- `-renamesourcefileattribute SourceFile`:不保留源文件名与行号,异常栈里没有源码线索。
  排错改用日志文案(`ModuleLogger`)与本地 `mapping.txt`(在 `/app/build` 下,已被 gitignore)。

验证方法:构建后对 `classes.dex` 跑 `dexdump -f`,确认
`Lgithub/shadowbaby/wechatxposed/hook/XposedInit;` 的 `initZygote` 以及各 hook 类的
`beforeHookedMethod` / `afterHookedMethod` / `replaceHookedMethod` 都在。

## 行为回归测试

`tests/hook-regression/` 用独立 `app_process` 进程运行本模块与参考实现,
比较 Hook 注册目标、参数、回调模式、反射调用顺序及返回值;用法见该目录的 `README.md`。
