### 命名说明（项目化 / 语义化）

原 apk 的混淆包 `a`/`b`/`c` 与包内类名互相遮蔽（如 `b` 包内引用 `c.a` 会被 javac
解析成 `b.c` 类的字段 `a`），无法直接编译。重建时把混淆名整体迁移为语义化命名：

- 包：`a`→`github.shadowbaby.wechatxposed.hook.rebuild.annotation`；`b`→`...rebuild.loader`；`c`→`...rebuild.support`
- 类：`b.a`→`WxComponentRegistry`、`b.b`→`ModuleLogger`、`b.c`→`InMemoryDexLoadHook`、
  `c.a`→`WxComponentHooks`、`c.b`→`CallMethodBypassHook`、`c.c`→`VerifierMethodReplacement`
- 字段：`f0..f13a` → 语义名（`LOG_POOL`/`LOADER_POOL`/`HOOK_POOL`/`BYPASS_POOL`/`WX_COMPONENTS`/
  `mode`/`componentId`/`bypassMode`/`hostClassLoader` 等）

### 可读性重构(在语义化命名之后)

原混淆类 `c.C0000`/`c.C0001` 是每个 Java 调用的纯转发包装(`listAdd(Object,Object)` 之类),
把每个调用点污染成不可读形式;`XposedInit.initZygote`、`WxComponentHooks.inject`、`c.b` 则是
`while(true) switch(state)` 状态机。这两层已去除:

- 删除 `ReflectBridgeA`/`ReflectBridgeB`,调用点直接用 `XposedHelpers` 或语言自带方法。
  受检异常改为向上传播(`WxComponentHooks.inject` 声明 `throws Throwable`),
  不再靠 `RuntimeException` 包装去绕过方法签名。
- 状态机展开为顺序代码:`XposedInit.initZygote` 只剩 4 行;`WxComponentHooks.inject`
  按 componentId 拆成 `hookBase`/`hookCore`/`hookThemes`/`hookDonation` 四个方法。
- 机器变量名改为语义名(`s73` 一类下划线常量、`arrayList22` 一类编号局部量全部替换);
  `msgId`、查询类型、bypassMode 改为具名常量。
- 字符串池与解码调用已整体移出源码,详见下节「字符串池抽取(第三阶段)」。
- 行为等价性由 `tests/hook-regression` 对照原版 DEX 验证(74 项检查全通过)。

### 字符串池抽取(第三阶段)

上一步把解码结果提升为具名常量后,池本身仍留在源码里:五个 `short[]` 池合计约 1.9k 项,
外加每类各自的 `decode(...)` 辅助方法,占了大半屏幕,且与业务逻辑无关。本阶段把它整体移出:

- 池原文 + 「偏移 / 长度 / key / 常量名 / 明文」对照表移到 `docs/StringPools.java`。
  该文件在 app 的 sourceSet 之外,**不参与编译、不打进 APK**(已验证:APK 的 classes.dex 里
  `StringPools` / `XorStrings` / `*_POOL` 字样计数全为 0)。
  可直接运行复核:`java docs/StringPools.java`(JDK 11+ 单文件源码启动),逐条比对池与明文。
- 源码里的 `decode(...)` 调用改为最终字符串字面量;池数组、`*_KEY` / `*_OFFSET` / `*_LENGTH`
  常量与 `decode(...)` 辅助方法一并删除。`rebuild/XorStrings.java` 已无引用,随之删除。
- 非 ASCII 字面量(微X自身混淆类名如 `c. َˉ.ᴖˉ`)按 `\uXXXX` 转义写,避免编码依赖。

运行时行为不受影响:原始混淆类名只作为字符串常量传给 `findClass`,与 Java 包名无关;
各类注释里保留原混淆名映射(如 `CallMethodBypassHook` 即原始的 `c.b`)。

## CallMethodBypassHook 核心控制流（decompiled_bad/sources/c/b.java 还原）

`beforeHookedMethod` 按 `bypassMode` 分流（hashCode 选择子：`۟ۤۙ`=0、`ۖۤۤ`=1、default=2）：

- **bypassMode=0（verifier6 校验拦截，args=[int msgId, Object[] params]）**：
  - msgId==130：遍历 params 匹配 `"param"` → 命中则 `setResult("true")`（L10246）
  - 白名单校验链（构造 `"null:equalsjava.util.Objects"` 反射工具串，hostClassLoader findClass）：
    远端返回类方法失败 → `callStaticMethod(c.ˉˉ.ٴʻⁱˏ, ⁱˏ)` → `setResult(false)` /
    补偿链 `c.ﹳﹶ.ʽᵔᐧٴ.ᐧٴ` → `setResult("true")`；命中 → `split("#")[0]` 取版本 →
    匹配 `"remote_rp_cmd"` → `setResult(null)`（L8018）或 `setResult(FEATURES)`（L629）
  - msgId==132：`callStaticMethod` + `callMethod(thisObject, "ˑᵎ", {805})`（L11823 伪造内部版本）
    → `setResult("8.0.49")`（L7273）
  - 其余 / 全链 try-catch 兜底：`setResult(Boolean.TRUE)`（L8381）
- **bypassMode=1（License 拦截）**：`callStaticMethod(c.ˉˉ.ٴʻⁱˏ, ⁱˏ)` 拿 lic（null → 透传）→
  `callMethod(obj, "ﹳˏ", {"LIC", str})`（L5816 伪造 LIC）→ 白名单校验链 →
  `callMethod(obj3, "ᐧٴ", {"LIC", ""})`（L9681）→ null 时
  `callStaticMethod(c.ﹳﹶ.ʽᵔᐧٴ, ᐧٴ)` + `callMethod(thisObject, "ˑᵎ", {805})` →
  `setResult("8.0.49")`；分支续接 `setResult("unlimited")`（L3255）/ `setResult(TRUE)`（L3382）

## 控制流混淆还原要点

原始代码是**状态机式 switch 跳转**：变量被 jadx 拆成 str/i/obj 几十个别名，
状态选择子是 `ReflectBridgeA.hashCode(str)` / `ReflectBridgeB.hashCode(str)`（= `String.hashCode()`，如
`"ۘۤۗ".hashCode() = 1740107`）。还原时按 case 值追踪状态转移即可。

字符串加密是**按调用点散布的 XOR key**（`short[] ^ key`）：
- 同一池内不同段落用不同 key（如 LOADER_POOL 用 7403 和 17407 两套）
- key 来自状态机分支（如 `i184 = 39633`；XposedInit 里 `s*s + 4020025` 推导）
- 部分段是**自身包内混淆类名**（`c.ˉˉ.ٴʻⁱˏ` 等），运行时作为合法类名传给
  `findClass`，不需要还原成 ASCII
