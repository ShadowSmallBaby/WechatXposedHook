# 微信 8.0.50–8.0.79 版本适配路线（二开工程）

> 2026-10-22。前提：上游（`fkzhang/WechatUnrecalled` / 微X 2.44 / X 3.0）已停止更新，
> 上游 `xmetadata/wx6/pr/` 最新只到 `P_8049`（2026-10-22 查询），不会再有新版本参数。
> 本仓库转为**二开工程**：后续微信版本的身份参数、核心兼容、打包与发布全部自维护。
>
> 基线：微信 8.0.49 + X 3.0 117 + x30 单 APK（`docs/x30-replica.md`）。
> 目标区间：**8.0.50–8.0.79**；其中 `75/73/69/59/52` 无具体版本号，
> 共 **25 个候选**（即最终适配范围）。
>
> 本文是版本适配的**单一事实源**；包体/密钥细节见 `docs/extension-pack-chain.md`，
> 方法论见 `docs/extension-pack-methodology.md`。

## 0. 结论摘要

1. **`pr/P_<微信版本>` 是唯一强版本绑定的文件**：它是该版本混淆类名到语义键的映射表
   （基线 `P_8049` 解出约 1410 条，`pr/P` 只有 82 条公共子集）。每个新版本必须自己生成。
2. 其余包（core、native loader、功能 dex、`H_p`/`M`/`S`/`Xmd`）**不按微信小版本发布**，
   可跨版本复用，但每个版本都要做兼容性回归；不兼容再走壳内补丁或自研 loader。
3. 适配工作量集中在四件事：**映射迁移 → 容器生成 → 清单更新 → 实机回归**，可脚本化。
4. 路线 A（保留原版核心）优先：沿用基线运行文件名，只替换 P 内容；只在核心拒绝时转路线 B。

## 2. 版本绑定关系

| 对象 | 是否随微信版本变 | 依据 | 复用策略 |
|---|---|---|---|
| `pr/P_<版本>` | **是** | 混淆类名每版重排；`P_8049` 约 1410 条 | 每版生成；相邻版本可先尝试复用 |
| `pr/P` | 否 | 公共子集（82 条） | 沿用 |
| `3.0/r/C` | 弱 | 模块框架 dex，由原壳作者编译 | 复用 + 回归 |
| `r/L`、`LD64` | 弱 | native 桥 / loader，按 ABI | 复用 + 回归 |
| `r/fp/*` | 否 | 模块功能 dex | 沿用 |
| `H_p`、`M`、`S`、`Xmd` | 否 | 模块配置 / 参数 / 资源 | 沿用 |
| `cfg/<role>.{c,s}` | 厂商签名边车 | 原样复制，不可重生成 | 换主体时同步 |

`P_8049` 的容器参数（已还原，作为新版本模板）：

```text
文件格式 = SHA-256(body)[32B] + body
body     = 97 c4 01 30 + msgpack 7 元组
           [版本, 5 位位置置换, f1 payload, f2 签名,
            f3 8B salt, f4 24B seed, f5 签名]
解密     = PBEWithMD5AndDES(password, salt, 1000) -> 16B key
           AES-128-CBC(IV = payload[:16]) -> msgpack map
密码公式 = trim(MD5(常量排列 + 7 位后缀))
基线值   = 后缀 0002318 / 排列 C S1 K / salt d160390cf774897a
           password ac282e135a29e137cf97b7677676c520
```

## 3. 两条技术路线

### 路线 A：保留原版核心（默认）

保留 x30 里原版 `classes.dex` 与 native loader，只替换版本参数。

- **文件发现技巧**：运行目录里的文件名是厂商内容 ID（`P_8049` = `6d6586c9…`），
  不可由角色名推导。二开时不追新 ID，而是**沿用基线的运行文件名，替换其内容**，
  核心按已知文件名读取即可。
- P 容器首字段是版本串 `b"0"`，没有微信版本号字段，内容替换不会触发版本判断。
- 签名槽位可能被校验：本模块已有 `自签放行（已移除）`，实机验证优先。
- 适用：核心对本版本的函数签名/偏移仍然成立；日志无 `SIGSEGV`、`Bad range`、
  `Module load error`。

### 路线 B：自研壳 / loader（兜底）

在 x30 的 compat dex 层接管参数选择、容器解密与加载。

- 运行名、密码、边车全部自定义，不再受厂商 ID 限制。
- 代价：需要复刻原 core 的类加载顺序与 native 桥协议。
- 触发条件：路线 A 在目标版本上稳定复现以下任一现象——
  `13x` 后 native 崩溃、功能包解密前崩溃、`Module load error`、菜单不显示且非身份问题。

判定顺序固定：**先 A 后 B**，单版本单变量对照，禁止同时换核心与参数。

## 4. 单版本标准作业流程（SOP）

> 命令级明细（采集、映射迁移、容器生成、登记、验证、回滚）见
> `docs/version-adaptation-sop.md`；本节只保留步骤骨架。

### Step 0 采集

- 获取目标版本官方 APK（国内渠道为主，Play 版单列），记录：
  包名、`versionCode`、`versionName`、签名证书 SHA-256、ABI、`classes*.dex` 数量。
- 证据落到 `build/analysis/<version>/`；在版本矩阵补行。

### Step 1 基线对齐

- 解包 dex，统计类/方法数量，与 8.0.49 对比规模变化。
- 用现有工具：`scripts/dex_inspect.py`、`scripts/scan_xmetadata_manifest.py`。
- 记录高价值锚点类（`LauncherUI`、`ChattingUI`、设置页、消息/支付相关）的结构签名。

### Step 2 映射迁移

以 `P_8049` 的键表为种子，在目标 dex 中重新定位每个语义键：

1. **结构指纹**：继承链、接口集合、方法数量与签名形状、字段类型、注解。
2. **字符串/资源锚点**：类内字符串常量、资源 ID、`R` 引用、XML 名称。
3. **调用关系**：与已锚定类的调用边、回调注册点。
4. **相邻版本优先**：`8.0.50 → 8.0.51` 的差异远小于跨多个版本；
   每版只对变化部分重新匹配，未变化的键直接继承。
5. **置信度分级**：高（唯一匹配）/ 中（多候选）/ 低（仅语义猜测）。
   低置信度键必须人工复核或实机日志闭环。

输出：`{语义键: 目标混淆类名}` 的完整映射与差异报告。

### Step 3 生成参数容器

- 按基线 msgpack 结构序列化映射（键顺序稳定，便于哈希去重）。
- 用模板密码公式生成容器；密码推导失败时，用现有 `PbePasswordHook` /
  `DigestProbe` 在实机抓取 PBE preimage 后再离线复现。
- 外层加 `SHA-256(body)` 32B 前缀，写入 `xmetadata/wx7/pr/P_<版本>`。
- **映射哈希去重**：映射内容相同的版本共用一份容器，矩阵中标注“复用 P_80xx”。
- 离线自检：

  ```bash
  python -X utf8 scripts/decrypt_wx244.py xmetadata/wx7/pr/P_8050 -o build/scratch/p8050
  # 解出 msgpack map 后，抽 10 个高价值键与目标 dex 对照
  ```

### Step 4 登记与打包

必须同步修改的固定清单（运行名/尺寸是硬编码，漏一处就会静默跳过）：

| 位置 | 改动 |
|---|---|
| `scripts/runtime_names.py` | `UTILITY` 增加 `pr/P_<版本>` 的运行名 |
| `scripts/build_x30_min.py` | `BASE_PACKS` 换成当前目标参数 |
| `scripts/build_release_packs.py` | `COMMON` 同步 |
| `scripts/reverse_pack_to_xmetadata.py` | `LAYOUT` 逆推表 |
| `app/.../deploy/FeaturePackRestorer.java` | `X30_BASE_NAMES` 与 `X30_BASE_SIZES` |
| `docs/extension-pack-chain.md` | 参数文件密码/尺寸对照表 |

生成与构建：

```bash
python -X utf8 scripts/build_x30_min.py --source xmetadata/wx7 \
    -o build/generated/x30_min --assets app/build/generated/featurepacks/wx30
./gradlew :app:assembleLegacyDebug
```

### Step 5 验证

1. **离线**：容器可解密、映射条目数与基线差异在预期内、文件尺寸/哈希与清单一致。
2. **构建**：`verify_featurepack.py` 通过；资产 zip 内文件名/尺寸与 Java 清单一致。
3. **实机**：A13 与 A16 各一轮；重启微信两次（首次恢复、二次加载）；检查日志：
   - 通过：`feature packs[x30]: restored 26 file(s)`、`X: Module loaded successfully!`
   - 失败：`SIGSEGV`、`Bad range`、`Module load error`、`dex buffer: 0 B`
4. **功能矩阵**：菜单显示、会话/朋友圈入口、消息类功能、支付/转账只读检查、
   扩展包 sf/mf/af 初始化。

### Step 6 发布与回滚

- 标记矩阵状态为 `✔`，证据与映射哈希归档。
- 保留上一版本 P 文件与 zip；异常时只回滚参数文件，不动核心。

## 5. 自动化规划

现有可复用：`decrypt_wx244.py`（容器解析/解密）、`runtime_names.py`、
`build_x30_min.py`、`build_release_packs.py`、`verify_featurepack.py`、
`dex_inspect.py`、`scan_xmetadata_manifest.py`。

建议新增（按落地顺序）：

| 脚本 | 职责 |
|---|---|
| `scripts/import_wechat_apk.py` | 读取 APK 元数据、导出 dex、生成版本记录 |
| `scripts/migrate_param_map.py` | 基于指纹/调用图迁移 `P_<版本>` 映射，输出置信度 |
| `scripts/build_param_container.py` | 映射 -> `P_<版本>` 容器（含 32B 前缀与自检） |

CI 增加两项硬校验：容器离线解密回读、`FeaturePackRestorer` 清单与产物逐一匹配。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| P 密码公式的后缀每版可能不同 | 容器生成后核心解不开 | 先复用基线公式；失败用 PBE 探针抓取 |
| 运行名固定 ID 不可推导 | 核心找不到参数文件 | 路线 A 沿用基线文件名替换内容 |
| 核心跨版本不兼容 | native 崩溃/加载失败 | 路线 B 接管加载；或壳内补丁 |
| 国内版 / Play 版混淆不同 | 同一版本需要两份映射 | 矩阵增加渠道字段，分开生成 |
| 自动迁移误报 | 功能静默失效 | 置信度分级 + 高价值键人工复核 + 实机日志 |
| 32 位 ABI 资源缺失 | 老设备无法加载 | 保留壳内 32 位 loader，单独回归 |
| 证据不可复现 | 无法定位回归 | 每版固定 `build/analysis/<version>/` 目录与命令记录 |

## 7. 验收标准（DoD）

单个版本同时满足以下条件才算 `✔`：

- [ ] `P_<版本>` 离线解密等于输入映射，条目数与差异报告一致；
- [ ] `xmetadata/wx7` 源文件通过 32B 前缀校验；
- [ ] 运行目录 26 + 6 个文件与 `FeaturePackRestorer` 清单/尺寸完全一致；
- [ ] A13/A16 实机启动无 native 崩溃、无 `Bad range`、无 `Module load error`；
- [ ] 菜单、会话、消息、扩展包四项功能回归通过；
- [ ] 证据与映射哈希归档，版本矩阵状态更新。

## 8. 维护约定

- 版本命名统一 `P_<微信版本去点>`，如 `P_8050`；空号不建文件。
- 一次适配一个 commit，提交信息带微信版本、`versionCode`、映射哈希。
- 参数文件内容变化才重新生成；仅运行名不同不算新参数。
- 核心/native 不做“顺手升级”：先单变量验证，再合并。
- 本文档是矩阵的唯一来源；其他文档只引用，不复制矩阵。
